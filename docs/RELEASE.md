# 发布、回滚与热修复

状态：流程规范，尚无发布版本。首个建议目标为 `v0.1.0`。

## 1. 可发行的定义

能够从固定源码和锁定依赖构建；生成的完整安装包可在目标干净机器安装与运行；真实 Harness/API/工作流主路径通过；升级、数据迁移和回滚方案已验证；发布包、版本、校验值和证据一致。

`main` 仅接受满足上述条件的 release/hotfix。开发服务器运行、打包成功或单元测试通过均不足以放行 main。

## 2. 进入 release

发布负责人依据各任务负责人的自审与验证证据，核对 v0.1 范围、FR/QA 矩阵、已知问题与依赖基线后，从最新通过检查的 develop 创建 `release/v0.1.0`。版本冻结后不加入新需求。必要修复先走普通 feature → develop 的测试与自审，再从 release 建 `feature/release-fix-<issue>`，仅挑选已自审修复，通过小 PR 进入 release，并由移植负责人重新验证兼容性及记录自审。不能为取一个修复而把 develop 后续新需求全部并入 release。

## 3. main 合并门槛

- [ ] 关联发行任务、候选提交 SHA、确定的目标平台与版本。
- [ ] 所有静态检查、单元、契约、集成和最终安装包端到端通过。
- [ ] FR-01 至 FR-10 及必需 QA 场景完成，有日志/步骤记录。
- [ ] 真实 DeepSeek API 冒烟通过，测试费用与模型标识可追溯。
- [ ] 无 P0/P1；P2 已知问题写入发布说明，发布负责人自审并记录接受理由。
- [ ] 包含 runtime 与所需依赖，普通用户无需另装开发工具。
- [ ] 应用数据库和 Harness 日志迁移、备份/恢复及失败演练通过。
- [ ] 轻量指标有实测数据；超预算已有接受的 ADR，不能默默改口径。
- [ ] 安装包、哈希、依赖/许可证清单、发布说明和用户指南齐全。
- [ ] 发行签名策略由发布负责人核验并记录；采用签名时验证证书和签名；暂以未签名包分发时明确标注状态、系统提示和 SHA-256，不宣称已签名。
- [ ] 发布负责人已记录最新候选提交的自审结论，讨论解决且无管理员绕过。
- [ ] main 合并候选对应的内容已经构建验证；目标 main 变化必须重建/重审候选。

CI 自动化尚未建立，以上是必需条件；不能创建永远成功的占位 `release-ready` 检查。

## 4. 发布步骤

1. 创建 release → main PR，附候选包与清单，验证 PR 的合并候选内容。
2. 发布负责人自行审查最新候选及证据，所有门槛通过后使用 merge commit 合入 main，无需他人批准。
3. 在 main 合并 SHA 上构建/校验发行产物。若与已测候选不是相同内容/配置，重新执行安装包验收，不能套用旧证据。
4. 对通过验证的 main 提交创建 `v0.1.0` tag，发布安装包、SHA-256、发布说明、许可证清单和已知问题。无成功构建不得先打正式 tag。
5. 创建 main → develop 回合 PR，同步版本和修复；如存在活跃 release，另建对应回合 PR。
6. 回合检查与审查通过后清理 release 分支。保留 tag、构建日志与旧版安装包供追溯。

CI 可以使用 GitHub Actions 等托管构建机；这不改变产品运行时无云电脑、数据在本地的要求。任何将真实用户数据上传 CI 的做法都不属于该授权。

## 5. 回滚

发布问题先停止新版本分发，公告影响范围。代码回滚使用可追溯的 revert 或新 hotfix，不重写 main/tag 历史。

应用数据不保证向旧 schema 反向兼容。降级前关闭应用，备份当前数据；只有兼容性已验证才直接回退二进制，否则恢复升级前备份到独立目录。恢复备份后产生的新数据如何保留必须说明，不自动覆盖。Harness home 与应用数据库作为同一备份集处理。

## 6. hotfix

从生产 main/tag 建 `hotfix/v0.1.1`；负责人重现问题、修复、回归并完成自审，满足同等级打包门槛后 PR 到 main。发布补丁 tag 后回合 develop 与活跃 release。紧急只改变优先级，不取消发布门槛。

## 7. 版本与记录

采用 SemVer，首版 `0.1.0`；候选 `0.1.0-rc.1`，候选 tag 不等于生产发布。应用版本、安装元数据、发布说明与 tag 一致；数据库 schemaVersion、工作流 schemaVersion、IPC protocolVersion 分开管理并记录兼容矩阵。
